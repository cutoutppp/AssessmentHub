## 1. ปัญหาที่ต้องการแก้

| ใคร | ปัญหา |
|---|---|
| งานวัดผล | ต้องอ่านข้อสอบคนอื่นเพื่อจับผิด หาไม่ค่อยเจอ เสียเวลา และรู้สึกเป็นงานจับผิดกัน |
| งานวัดผล + ครู | ตรวจบนกระดาษ ตีกลับแล้วพิมพ์ใหม่หลายรอบ เปลืองกระดาษ/หมึก |
| ครู | ต้องตีตาราง วผ.29 ใน Word เอง กรอกรหัสตัวชี้วัดซ้ำๆ |
| ระบบเดิม (IOC) | รับข้อสอบผ่าน JSON ที่ครูให้ AI ของตัวเองสกัด → รูปแบบไม่แน่นอน → โค้ดต้องปะผุ (fallback ซ่อม JSON) และสมการ/ข้อสอบหลายกลุ่มสาระไม่รองรับ |

> **ข้อตัดสินใจ 12 พ.ย.: ความลับของข้อสอบไม่ใช่ข้อกังวลหลัก** — ส่งข้อสอบไปบริการ AI ภายนอกได้ (รวมแบบฟรี), ไม่ต้องออกแบบสิทธิ์เข้มเท่าข้อมูลลับ
> ข้อที่ยังคงไว้: เฉลยไม่พิมพ์ลงเอกสาร (เพื่อวิเคราะห์การกระจาย ไม่ใช่เพราะความลับ), ข้อมูลครู/นักเรียน/รหัสผ่านไม่ขึ้น Public GitHub ตาม CLAUDE.md, `samples/` ไม่ขึ้น git
> **ความเสี่ยงที่ยังต้องกัน:** ข้อสอบ **ทั้งชุด** หลุดไป **พร้อมกับ** ชื่อครู/ชื่อโรงเรียน/รหัสวิชา
> → กติกาเวลาส่งให้ AI/OCR ภายนอก: (1) ตัดหัวกระดาษ ชื่อครู ชื่อโรงเรียน รหัสวิชา ห้อง ภาค/ปี ออกก่อนส่ง (2) ส่งเป็นรายข้อหรือก้อนเล็ก ไม่ส่งทั้งฉบับในคำขอเดียวเมื่อเลี่ยงได้ (3) ไม่ส่งเฉลยไปพร้อมโจทย์ยกเว้นงานตรวจเฉลย ซึ่งทำทีละข้อ
> หัวข้อด้านล่างที่พูดถึง "ความลับข้อสอบ" ให้ถือว่าผ่อนลงตามนี้

## 1.1 ขั้นตอนจริงในปัจจุบัน → สิ่งที่ระบบจะทำแทน

| ขั้น | ปัจจุบัน | ระบบใหม่ | เฟส |
|---|---|---|---|
| 1 | ครูจัดทำข้อสอบตามโครงสร้างรายวิชา | ทำ วผ.29 บนเว็บก่อน (ดึงหน่วย/ตัวชี้วัด/คะแนนจากโครงสร้างรายวิชา) → ใช้เป็นกรอบออกข้อสอบ | R1 |
| 2 | พิมพ์ข้อสอบ + **เขียนใบแจ้งจำนวนถ่ายเอกสารด้วยมือ** | **ออกใบแจ้งถ่ายเอกสารอัตโนมัติ** (วิชา/ห้อง/จำนวนนักเรียน+สำรอง/จำนวนหน้า/วันสอบ) — ไม่ต้องพิมพ์ข้อสอบมาส่งตรวจ | R1 |
| 3 | ส่งข้อสอบ (กระดาษ) ให้งานวัดผลตรวจ | ส่งบนเว็บ: วผ.29 + ไฟล์ข้อสอบ + เฉลย (เก็บในระบบ) + การ์ดตรวจอัตโนมัติ | R1 (แนบไฟล์) / R2 (ตรวจไฟล์อัตโนมัติ) |
| 4 | ผ่าน → ส่งถ่ายเอกสาร | กด "อนุมัติ" → สถานะ "พร้อมถ่าย" + ใบแจ้งถ่ายเอกสาร → ฝ่ายถ่ายเอกสารเห็นคิว | R1 |
| 5 | ไม่ผ่าน → ส่งกลับแก้ วนส่งใหม่ (พิมพ์ใหม่ทุกรอบ) | กด "ตีกลับ" พร้อมเหตุผลรายข้อ → ครูแก้แล้วอัปโหลดฉบับใหม่ (เก็บทุกเวอร์ชัน) — **ไม่พิมพ์จนกว่าจะผ่าน** | R1 |

ผลรวม: กระดาษถูกพิมพ์ **ครั้งเดียว** คือตอนถ่ายเอกสารจริง

### 1.2 การอนุมัติ 2 ชั้น + รหัสรับรอง

```
ครูส่ง ──▶ [ชั้น 1: ระบบตรวจ] ──ไม่มี 🔴──▶ [ชั้น 2: วัดผลดูด้วยตา] ──อนุมัติ──▶ ออกรหัสรับรอง
              │ มี 🔴                           │ ตีกลับ + เหตุผล
              ▼                                 ▼
          ครูแก้เอง (ยังไม่ถึงมือวัดผล)        ครูแก้ → ส่งใหม่ (เริ่มชั้น 1 ใหม่)
```

- ชั้น 1 กรองข้อผิดเชิงกลไกออกก่อน → วัดผลเหลือดูเฉพาะเรื่องที่ต้องใช้คน (ความเหมาะสมของเนื้อหา ความชัดของรูป ฯลฯ) และเห็นการ์ดสรุปประกอบ
- **รหัสรับรองออกได้เฉพาะเมื่อผ่านทั้ง 2 ชั้น** เช่น `PTNK-2569-2-MID-ค21101-A7K3`
- รหัสผูกกับ **ไฟล์ฉบับที่อนุมัติ** (เก็บค่า hash ของไฟล์) — ถ้าครูแก้ไฟล์หลังอนุมัติ รหัสเดิมใช้ไม่ได้ ต้องส่งตรวจใหม่
- ระบบฝังรหัสลงในหัวกระดาษข้อสอบ + ใบแจ้งถ่ายเอกสาร (พร้อม QR ไปหน้าตรวจสอบ)
- **ฝ่ายถ่ายเอกสารดาวน์โหลดไฟล์ที่อนุมัติจากระบบโดยตรง** (ไม่รับไฟล์/กระดาษจากครู) หรือสแกน QR ยืนยันก่อนถ่าย → ป้องกันการถ่ายฉบับที่ยังไม่ผ่าน
- ทุกการอนุมัติ/ตีกลับบันทึกว่าใคร เมื่อไร เหตุผลอะไร

### 1.22 วผ.29 แบบละเอียดรายข้อ — *แนวคิด ยังไม่ตัดสินใจ*

- วผ.29 ทำได้ถึงระดับรายข้อ: ข้อที่ · ตัวชี้วัด · Bloom · พฤติกรรมที่วัด · (ตัวโจทย์ย่อ) · เฉลยเก็บในระบบ

- แนวคิด: **ให้ระบบใช้ agent แทนครู** — นำ pipeline ของ ExamGenerator (เช่น `src/docx_builder.py`, ตัว export Google Forms) มาเป็นเครื่องยนต์กลาง ครูแค่ป้อน/เลือกข้อสอบแล้วกดปุ่ม; AI รันผ่านบัญชีกลาง; ข้อมูลผ่าน schema + validator เดียวกัน
- ถ้าเลือกแนวนี้: ต้องสำรวจโค้ด ExamGenerator ว่าใช้ซ้ำได้แค่ไหน ก่อนวางแผน R3

### 1.3 ชั้นตรวจด้วย AI ตัวเล็ก (แนะนำเท่านั้น) — *ยังระดมความคิด ไม่ได้ตัดสินใจ*

- ตำแหน่ง: เสริมในชั้น 1 หลัง parser (R2) แยกข้อได้แล้ว — เฟสหลังกลางภาค นำร่องปลายภาค
- ผลจาก AI = 🟡 เสมอ ("AI สังเกตว่า...") ไม่บล็อกการส่ง ครูกด รับทราบ/แก้แล้ว วัดผลเห็นสรุป
- งานที่ให้ AI: ตรวจเฉลยเทียบโจทย์ (เฉลยผิด/ถูกหลายตัว), โจทย์กำกวม/ปฏิเสธซ้อน, ตัวลวงอ่อน, ยืนยันคำผิดที่โค้ดคัดมา, เสนอ Bloom/ตัวชี้วัด, เนื้อหาอ่อนไหว
- **Bloom (ต่อจาก 1.22 รายข้อ):** AI เสนอระดับรายข้อพร้อมเหตุผลสั้น; เตือนเมื่อ (ก) ระดับที่ครูเลือกห่างจากที่ AI ประเมิน ≥2 ระดับ (ข) คำกริยาของตัวชี้วัดสูงกว่าข้อสอบที่วัดจริง เช่น ตัวชี้วัด "วิเคราะห์" แต่ทุกข้อเป็น "จำ" — ครูเป็นผู้ตัดสินสุดท้ายเสมอ (ผู้เชี่ยวชาญเองก็จัด Bloom ไม่ตรงกันเสมอไป)
- งานที่ห้ามให้ AI: นับข้อ, รวมคะแนน, 70:30, การกระจายเฉลย, ข้อซ้ำ → โค้ด
- ข้อสอบที่มีสมการ/คำนวณ: ข้าม
- ข้อควรระวัง: เตือนผิดในภาษาไทย (ต้องวัดความแม่นจากไฟล์จริงใน `samples/` ก่อนเปิดแต่ละหัวข้อ), ความลับข้อสอบ (API แบบเสียเงินที่ไม่นำข้อมูลไปเทรน, ไม่ส่งชื่อครู/โรงเรียน)
- ต้นทุนคาดว่าต่ำ (ราว 200 วิชา/รอบสอบ) — ยืนยันราคาเมื่อเลือกโมเดล

## 2. หลักคิด

1. **ครูตรวจตัวเองก่อนส่ง, เครื่องจับข้อผิดเชิงกลไก, วัดผลดูแค่การ์ดสรุป** — เลิกจับผิดกันบนกระดาษ
2. **ลงแรงเมื่อไหร่ ต้องได้คืนทันที** — ทุกช่องที่ครูกรอกต้องไปโผล่ในเอกสารที่ครูต้องใช้อยู่แล้ว
3. **กรอกครั้งเดียว ใช้หลายเอกสาร** — ข้อมูลชุดเดียวสร้าง วผ.29, บันทึกขออนุมัติ, การ์ด QC, (อนาคต) ข้อสอบพร้อมพิมพ์/คลังข้อสอบ
4. **ส่วนที่ยากต้องไม่ขวางส่วนที่ทุกคนต้องใช้** — วผ.29 ไม่ต้องอ่านไฟล์ข้อสอบ จึงใช้ได้ทุกกลุ่มสาระ รวมคณิต/เคมี
5. **ระบบไม่ต้องเข้าใจสมการ แค่ไม่ทำมันพัง** — สมการ/รูป = บล็อกทึบ ข้ามการตรวจ
6. **ข้อมูลไม่ผ่าน schema = ไม่บันทึก แล้วบอกครูว่าแก้ตรงไหน** — ห้ามเดาซ่อม (บทเรียนจาก IOC)
7. **ครูเลือกเอง: เฉลย ตัวชี้วัด Bloom** — AI เป็นแค่ปุ่มเสนอแนะ (ถ้ามี)

## 5. R1 — สิ่งที่ครูและวัดผลจะเห็น (กลางภาค)

**ครู**
1. เข้าสู่ระบบ → เห็นวิชาที่ตัวเองสอนภาคนี้
2. เลือกวิชา + กลางภาค/ปลายภาค → ระบบดึงหน่วย ตัวชี้วัด และคะแนนสอบของวิชามาให้
3. กรอก: ปรนัยกี่ข้อ ข้อละกี่คะแนน / อัตนัยกี่ข้อ คะแนนรายข้อ → เห็นคะแนนรวมและสัดส่วน 70:30 ทันที
4. ตาราง: แต่ละแถว = หน่วย + ตัวชี้วัด + ระดับ Bloom + เลขข้อ (พิมพ์ช่วงได้ เช่น `1-5, 8`)
   - แถบ "ข้อที่ยังไม่ได้จัด" นับให้สด
5. กรอกเฉลยปรนัยแบบพิมพ์ต่อกัน (`กขคง...`) → เห็นกราฟการกระจาย ก/ข/ค/ง
6. แผงตรวจ 🔴/🟡 เป็นภาษาคน เช่น "คะแนนรวม 53 แต่คะแนนสอบวิชานี้ 55 (ขาด 2)"
7. ปุ่ม: บันทึกร่าง · ดาวน์โหลด วผ.29 (.docx) · ส่งงานวัดผล (กดได้เมื่อไม่มี 🔴)

**ผลตอบแทนครู:** ได้ วผ.29 + บันทึกขออนุมัติที่เติมข้อมูลครบ, ไม่ถูกตีกลับเรื่องตัวเลข, ส่งบนเว็บไม่ต้องพิมพ์

**งานวัดผล / หัวหน้ากลุ่มสาระ**
- ตารางทุกวิชา: ยังไม่ทำ / ร่าง / ส่งแล้ว / ตีกลับ / อนุมัติ
- การ์ดสรุปต่อวิชา: ผ่าน/เตือนกี่รายการ, 70:30, ตัวชี้วัดครบไหม, **สถิติการกระจายเฉลย** (ไม่เห็นเฉลยดิบ)
- อนุมัติ/ตีกลับพร้อมเหตุผล — เก็บประวัติทุกรอบ

**เฉลย:** เก็บในฐานข้อมูลเท่านั้น ไม่ลงไฟล์ที่ export ไม่ลงกระดาษ ใช้ (1) ตรวจการกระจายตัวเลือกตอนนี้ (2) วิเคราะห์ข้อสอบหลังสอบในเฟส R5

## 6. R2 — QC Checker (ถ้าทันกลางภาค)

- ครูอัปโหลด .docx → อ่านในเบราว์เซอร์ (ข้อสอบไม่ออกจากเครื่อง) → รายงาน 🔴/🟡 พร้อมเลขข้อ → ครูไปแก้ใน Word ของตัวเอง
- ตรวจ: เลขข้อกระโดด/ซ้ำ, ตัวเลือกไม่ครบ/ซ้ำ, โจทย์ซ้ำ/คล้าย, อ้าง "จากภาพ" แต่ไม่มีรูป, **จำนวนข้อไม่ตรง วผ.29**, คำผิดพื้นฐาน
- รอบแรกเป็น **ตัวช่วยตรวจตัวเอง ไม่ใช่เกณฑ์ตีตก**; ไฟล์ที่อ่านไม่ออก = "ระบบยังไม่รองรับรูปแบบนี้" ไม่ใช่ความผิดครู
- **ต้องมีไฟล์ข้อสอบจริง ≥10 ไฟล์จากหลายกลุ่มสาระ** ใน `TestBlueprint/samples/` (🔒 ไม่ขึ้น git) ก่อนเขียน spec

## 7. สถาปัตยกรรม (วางใหม่ ไม่ผูกกับระบบเดิม)

### ข้อเสนอ: หน้าเว็บ static + Supabase

| ชั้น | เลือก | เหตุผล |
|---|---|---|
| หน้าเว็บ | HTML/JS แยกโมดูล (หรือ Vite + framework เล็ก) โฮสต์ static (GitHub Pages/Netlify) | ไม่มี server ต้องดูแล, สร้าง .docx ฝั่งเบราว์เซอร์ได้เหมือน assessment-plan |
| ฐานข้อมูล | **Supabase Postgres** | มี schema จริง ตรวจชนิดข้อมูลได้ ต่างจาก Sheet ที่เก็บ JSON เป็นข้อความ |
| การยืนยันตัวตน | Supabase Auth (แนะนำ Google Sign-in ถ้าครูมีบัญชีโรงเรียน; ไม่งั้น email+รหัส) | ไม่ต้องเขียนระบบ login/PIN/JWT เอง |
| สิทธิ์เข้าถึงเฉลย | **Row Level Security** ในฐานข้อมูล: เจ้าของอ่าน/เขียนของตัวเอง, วัดผลอ่านสถิติผ่าน view ที่ไม่มีคอลัมน์เฉลย | ความปลอดภัยอยู่ที่ฐานข้อมูล ไม่ขึ้นกับโค้ดหน้าเว็บ — ปิดช่องโหว่ประเภท token ปลอม/โหมด log ของระบบเดิม |
| ข้อมูลรายวิชา | ไฟล์ `courses_2_2569.json` เดิม (อ่านอย่างเดียว) → นำเข้าตาราง `courses` | ใช้ของที่มีและตรวจแล้ว |
| การตรวจ (validator) | ฟังก์ชัน JS ตัวเดียว + ฐานข้อมูลบังคับเงื่อนไขพื้นฐาน (constraint) | ไม่ต้องเขียน validator 2 ภาษา |

**ทางเลือกอื่นที่พิจารณา**
- *Google Sheet + GAS (แบบ IOC/masterdata):* ฟรีและคุ้นเคย แต่ไม่มี schema, สิทธิ์รายแถวทำยาก, เก็บเฉลยก่อนสอบเสี่ยง
- *TeacherHub-Backend (FastAPI):* มี login อยู่แล้ว แต่ข้อมูลไปจบที่ GAS อยู่ดี และพบจุดอ่อน: `JWT_SECRET_KEY` มีค่า fallback ที่เดาได้ และโหมด `AUTH_MODE=log` ปล่อยคำขอที่ไม่มี token ผ่าน → ถ้าใช้ต้องแก้ก่อน

**ข้อแลกเปลี่ยนของ Supabase:** เพิ่มบริการใหม่ 1 ตัวที่ต้องดูแล; ครูต้องมีบัญชีใหม่ (ถ้าใช้ Google Sign-in จะแทบไม่รู้สึก); แผนฟรีพอสำหรับโรงเรียนเดียว แต่ project ฟรีจะหยุดเมื่อไม่มีการใช้งาน 7 วัน (ต้องมีงานตั้งเวลาเรียกเป็นระยะ หรือจ่ายแผน Pro)

### ตารางข้อมูลหลัก (R1)

```
courses        (course_code, name, grade, learning_area, units jsonb, indicators jsonb, mid_points, final_points)
teachers       (user_id → auth, teaccode, name, dept, role: teacher|dept_head|measurement|admin)

blueprint_events (blueprint_id, at, by, action, note)     ← ประวัติ ส่ง/ตีกลับ/อนุมัติ

```

2. **การเข้าสู่ระบบ:** ครูทุกคนมีบัญชี Google ของโรงเรียนไหม (ถ้ามี → Google Sign-in)
3. **แบบฟอร์ม:** `วผ29 โครงสร้างของแบบทดสอบ-3.docx` เป็นฉบับสุดท้าย?
4. **เกณฑ์ 70:30:** ยอมคลาดได้กี่ % (ร่างใช้ ±5) — เป็นการเตือน 🟡 หรือห้ามส่ง 🔴
5. **บทบาท:** ใครอนุมัติ (หัวหน้างานวัดผล? หัวหน้ากลุ่มสาระ?) และต้องอนุมัติกี่ชั้นบนเว็บ (แบบกระดาษมีลงนาม 5 ระดับ)
6. **วันสอบกลางภาค** และวันที่ครูต้องส่งข้อสอบ
7. **ใบแจ้งถ่ายเอกสาร:** ขอแบบฟอร์มที่ใช้จริง, จำนวนนักเรียนรายห้องเอาจากแหล่งไหน (SGS?), สำรองกี่ชุด, ใครเป็นผู้รับคิวถ่ายเอกสาร
8. **ไฟล์ข้อสอบที่ส่ง:** รับ .docx อย่างเดียว หรือ .pdf ด้วย (วัดผลเปิดดูบนเว็บ)
